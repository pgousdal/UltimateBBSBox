# Delivery M0 report

## Result

M0 establishes contracts and validation without pretending the existing Mystic-first Ansible implementation already satisfies the future architecture.

## Repository audit

The starting repository provisions a hardened Debian host, serial/RS485 devices, Mystic BBS on metal, a network gateway, Mystic-specific backups, and node_exporter. This is useful implementation material but couples acquisition, runtime, backup, and service lifecycle directly to Mystic.

M0 deliberately does not delete or rewrite those roles. They are retained as the first integration to migrate through later contracts.

## Contracts delivered

- artifact v1: immutable object identity, provenance, preservation class, and explicit redistribution rights;
- endpoint v1: local process, TCP, SSH, serial, and remote-supervisor targets;
- service v1: service type, endpoint reference, menu/BBS exposure, direct-access policy, lifecycle, sharing, and scheduled maintenance;
- integration v1: automation level, runtime, installation steps including manual evidence, and qualification checks.

The validator also checks registry-level references: IDs are unique, services reference declared endpoints, `via_bbs` references actual BBS services, and integrations reference declared services.

## Explicit non-conformances carried into M1+

These are known debt, not hidden failures:

1. `roles/mystic_bbs` downloads Mystic directly to `/tmp` and installs it. It does **not** yet route acquisition through the immutable preservation archive. M1 must fix this before the generalized acquisition path is used.
2. `roles/mystic_bbs` always enables/starts Mystic. It does not yet obey the lifecycle manifest. M3 owns this migration.
3. `roles/backup` is Mystic-specific and backs up an installation tree rather than a generic separation of golden installation vs mutable service state.
4. `network_gateway` exposes configured ports directly; it is not yet the M4 session router/exposure-policy implementation.
5. Existing `.mpy` doors are files copied into Mystic, not Door Museum integrations.
6. Secrets-provider and state/export contracts are documented requirements but intentionally deferred from M0 implementation.
