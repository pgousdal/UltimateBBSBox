# M9.1b Debian DOSEMU2 + FreeDOS 1.4 provisioning

## Result: INCOMPLETE

The repository now has a preservation-only verifier in
`scripts/ubb_dos.py` (`verify_preserved_input` and
`provisioning_manifest`). It consumes only immutable M1 archive objects,
checks the metadata role, size, and SHA-256, and rejects runtime paths inside
the archive. It does not acquire network content or publish a runtime.

This is an implementation prerequisite, not qualification evidence. The
clean Debian snapshot still has no materialized M1 archive store and no
repository-owned DOSEMU2/FDPP build/install orchestration, so M9.1b remains
unqualified.

On the 2026-08-17 clean Debian replay, the existing M1 CLI was used to
materialize all three inputs. DOSEMU2 and FreeDOS matched their pinned hashes;
FDPP required the historical `git archive --prefix=fdpp-1.10/ HEAD | gzip -n`
form to reproduce the pinned 327,763-byte object. `provision-manifest` then
passed. The new build entrypoint reached the pinned FDPP source but did not
complete: Debian’s FDPP loader link still selected an incompatible libelf
architecture. No runtime was published and no qualification PASS is claimed.

The corrected Debian-native prerequisite is now encoded in the provisioning
path: enable the `i386` foreign architecture, install `gcc-multilib`,
`g++-multilib`, `libc6-dev-i386`, and `libelf-dev:i386`, then run a 32-bit
libelf link probe before Meson. FDPP receives an architecture-scoped Meson
environment (`-m32`, i386 pkg-config and library paths); host build targets are
not globally changed. Provisioning fails closed if the probe does not produce
an ELF32 executable.

Real Debian VM evidence confirms the original failure: FDPP's i386 loader
link used the amd64 `libelf.so`, producing `file in wrong format`. With
Debian `i386` multiarch, `libelf-dev:i386`, and the i386 Meson cross file, the
loader reaches the correct ELF32 libelf selection. The subsequent full
provision remains unqualified: the disposable FDPP/DOSEMU2 build still needs
the host/target split for FDPP's 32-bit loader versus DOSEMU2's host library
and the remaining DOSEMU2 optional dependency set. No runtime or boot PASS is
claimed from this run.

The entrypoint for the implemented preservation boundary is:

```text
python3 scripts/ubb_dos.py provision-manifest \
  --archive-root /var/lib/ultimate-bbs-box/archive \
  --runtime-root /opt/ultimate-bbs-box/dosemu2/82770aba3984
```

It is intentionally read-only: it verifies the DOSEMU2 object
(`8a08d605…`, 3,053,938 bytes), FDPP 1.10 object
(`fd6e4332…`, 327,763 bytes), and M1 `freedos-1.4-livecd` object
(`2020ff6b…`, 293,950,337 bytes) before any future build orchestration is
allowed to consume them. Acquisition remains exclusively through
`scripts/ubb_archive.py`/M1; provisioning never accepts a URL.

Debian is the canonical UBB production target. The current qualification host
is Ubuntu 26.04 LTS x86_64 and is recorded separately; Ubuntu is not used as a
production provisioning definition and no Ubuntu PPA is part of UBB.

The repository has no completed clean-Debian runtime qualification yet. QEMU
installed on the qualification host is not substituted for DOSEMU2.

The code exposes a Debian-first provisioning plan that fails closed for non-Debian
targets and requires an observed package version. FreeDOS metadata requires an
observed artifact, source URL, and SHA-256; it never invents the expected
`FD14-LiveCD.zip` identity or downloads directly into a runtime directory.

Once a Debian host and authoritative FreeDOS 1.4 LiveCD are available, the safe
sequence is: Debian package/source verification, M1 acquisition and checksum/
rights recording, bounded archive extraction, derived golden environment,
mutable working clone, then real DOSEMU2 boot and bidirectional COM1/PTY tests.
M9.1a is already complete; those tests are retained here only as the M9.1b
clean-provision smoke gate.
