# M9.1d DOSEMU2 serial investigation

## Status: COMPLETE

The existing M9.1c COM1 failure remains preserved: both host-to-guest and
guest-to-host COM1 tests reported `Error reading from device COM1: Unknown error
code` with the DOSEMU2-created PTY and an external socat PTY pair. No CTTY result
is treated as UART proof.

The disposable qualification VM is reachable and was inspected without changing
production state:

* Debian GNU/Linux 13 (trixie), kernel `6.12.101+deb13-amd64`, x86_64;
* pinned DOSEMU2 2.0pre9 revision 7076 at the recorded `/opt` path;
* the preserved FreeDOS LiveCD mount is present;
* no physical serial device or public network was used.

An initial direct invocation exposed a packaging/runtime issue: the wrapper could
not load `libdosemu2.so`/FDPP libraries until the pinned `lib`, `lib/dosemu`, and
`lib/fdpp` directories were supplied through `LD_LIBRARY_PATH`. With those paths,
`dosemu --version` reports 2.0pre9 revision 7076, but this does not prove a guest
boot or serial operation. A minimal FreeDOS boot/BIOS INT 14h/UART reproducer and
PTY termios trace still need to be run in the VM.

Subsequent disposable-VM execution established real guest evidence. Running as
the unprivileged qualification user with the `kvm` group, `HOME`, `TERM`, and the
pinned library paths set, DOSEMU2 emitted the FreeDOS 1.4 banner and kernel 2043.
The first attempt lacked a materialized `COMMAND.COM` tree; copying the preserved
`FDOS-x86` working content into the disposable `drive_c` resolved that specific
guest-root issue. The resulting process reached the FreeDOS language prompt and
executed under the headless QEMU/libvirt VM. This is real boot evidence, but it
is not COM evidence.

The current remaining blocker is narrower: a direct BIOS INT 14h/UART utility and
raw PTY attachment have not yet been run. The observed DOSEMU2 diagnostics also
show KVM permission and console/audio warnings when the environment is incomplete;
those are invocation issues, not proof of a serial regression. Therefore no
conclusion is yet justified among FreeDOS/FDPP interaction, PTY behavior,
DOSEMU2 serial regression, or backend unsuitability.
The canonical backend remains `PARTIALLY_QUALIFIED`; M9.1a, M9.1b, M9.1c, and
M9.1d remain incomplete. No fallback emulator was substituted.

## Deterministic harness result (continuation)

A repository-owned harness now prepares a disposable working tree, writes a
non-interactive `FDCONFIG.SYS`/`AUTOEXEC.BAT`, creates a raw PTY, launches the
pinned DOSEMU2 configuration, and waits for bounded `SERIAL.READY`/result-file
evidence.  The DOS probe is a small NASM-built `.COM` image using BIOS INT 14h;
it expects `41 42 43` and replies `UBB-OK`.

The harness was executed in the Debian VM.  DOSEMU2 again booted the real
FreeDOS kernel and FreeCOM, but the guest reported `Bad command or filename`
for the probe on the mapped C: drive, so no serial bytes were sent and no COM
claim is made.  This is a concrete qualification-harness/filesystem execution
failure, not evidence of a UART regression; the next investigation must make
the DOS executable visible to the guest before serial diagnosis proceeds.

### 8.3/path follow-up

The original `SERIALTEST.COM` stem exceeded eight characters. The harness now
uses strict DOS names: `C:\UBBQUAL\UBBTEST.COM`, `READY.RST`, and
`SERIAL.RST`, with a fresh writable disposable drive tree. This removes the
long-name ambiguity and avoids modifying preserved media. DOSEMU2 reached
FreeCOM and the AUTOEXEC `MD` command in that tree.

On the subsequent Debian run, DOS still produced neither readiness nor result
file. The host used the bounded FreeDOS-kernel banner fallback and sent
`41 42 43`; no `UBB-OK` reply was received. Current evidence is therefore:

* DOS boot/AUTOEXEC: PASS;
* strict-name materialization: PASS on the host tree;
* host PTY/DOSEMU2 COM1 exchange: FAIL (no guest reply);
* guest result-file persistence: not observed.

This is now a genuine serial or DOSEMU2 host-drive write-path failure to be
diagnosed with BIOS/UART status and syscall tracing; it is not claimed as COM
qualification or backend rejection.

## DOS-local FAT attempt

The harness now supports a disposable `mkfatimage16` filesystem attached as
DOSEMU2 drive D:, with the host directory retained only for boot inputs. The
image was attached and FreeDOS enumerated it as `D:`, but the current
`mkfatimage16` output could not be mounted by Debian's loop filesystem tools
after shutdown (`wrong fs type/bad superblock`). Consequently offline
`READY.RST`/`SERIAL.RST` evidence was not obtained and the SELFTEST gate remains
incomplete. No COM1 test was made from this path.

## SELFTEST gate

The utility now has a serial-free `SELFTEST` mode and the runner can select it.
The same real Debian VM run reached FreeDOS/FreeCom but produced neither the
`UBB-SELFTEST-EXECUTED` marker nor `READY.RST`/`SERIAL.RST`.  Thus the remaining
failure is earlier than COM: AUTOEXEC is not observably completing the DOS
program invocation (or the DOS host-directory write path is suppressing all
observable output).  COM1 was not retested after this result.

### mtools correction and current result

Inspection showed that `mkfatimage16` creates a 128-byte DOSEMU header followed
by a partition at byte offset 8832. Debian loop mounting is therefore the wrong
inspection method. `mtools` reads the image directly with:

    MTOOLS_SKIP_CHECK=1 mdir -i IMAGE@@8832 ::

The DOS-local round-trip now succeeds: FreeDOS creates `UBBQUAL`, and offline
inspection finds `READY.RST` and `SERIAL.RST`. `SELFTEST` contains:

    MODE=SELFTEST
    EXECUTION=PASS
    WRITE_PATH=PASS
    RESULT=PASS

`SELFTEST_GATE=PASS`. The storage classification is
`HOST_INSPECTION_METHOD_WRONG`, not FAT corruption.

Using the same image and utility in `EXCHANGE` mode then produced a genuine
serial failure: the host sent `41 42 43`, no `UBB-OK` arrived, and offline
`SERIAL.RST` contained `RESULT=FAIL`. No backend rejection is claimed.

## M9.1a follow-up: binary matrix harness

The original M9.1a contract requires byte-preserving COM1 transport (including
NUL, high-bit CP437 bytes, CR/LF, and ANSI escape bytes). The existing
`UBBTEST.COM` was extended with a `MATRIX` mode and the host runner now treats
the payload as raw bytes. The payload is:

```text
00010A0D1B20417F80B3C4DAFF1B5B33316D0D0AB3C4DA
```

This extension preserves the previously proven `SELFTEST` and `EXCHANGE` paths.
The first VM attempts exposed three probe defects: `recv_one` clobbered the
outer `CX` count, the short `MATRIX` command failed the minimum-tail-length
check, and mode detection inspected the wrong command-tail character. The
corrected code checks `M` at offset `82h` and preserves `CX` around `recv_one`.
A real combined matrix run then produced exact RX/TX and `RESULT=PASS`.

The final 2026-08-17 continuation rebuilt the probe from that source and added
fresh minimal (`0041FF`), raw 13-byte, and combined 23-byte runs. All were exact
in both directions. After a bounded FAT result-write settling delay removed a
host shutdown race, basic exchange passed 10/10 and the combined matrix passed
3/3. These results extend M9.1d's already complete BIOS-status root-cause proof;
they do not erase or reinterpret the chronological failures above.

## Serial boundary investigation

The failed result was:

    UBB_SERIAL_VERSION=1
    COM=1
    METHOD=BIOS
    RESULT=FAIL

An isolated PTY test was run in raw mode with byte-preserving termios. The
DOSEMU2 syscall trace then showed:

* `/dev/pts/0` opened successfully;
* raw termios applied (`IGNBRK|IGNPAR`, `CLOCAL`, no canonical/output mapping);
* the PTY modem ioctls returned `ENOTTY`, expected for a PTY;
* the serial backend read exactly `ABC` from the PTY.

Thus the first failing boundary was inside the guest BIOS serial status path,
not host PTY or DOSEMU2 PTY input.

The DOS probe was corrected to test the BIOS INT 14h line-status/data-ready bit
in `AH` (the previous probe incorrectly tested `AL`). With that single change,
the same Debian VM, DOSEMU2 revision, FAT image, PTY arrangement, and byte
sequence produced this offline result:

    RX=414243
    TX=5542422D4F4B
    RX_STATUS=PASS
    TX_STATUS=PASS
    RESULT=PASS

Therefore `COM1_HOST_TO_GUEST=PASS` and `COM1_GUEST_TO_HOST=PASS`. The primary
serial classification is `BIOS_INT14_RX_ERROR` in the qualification utility,
fixed by using the correct returned status register. DOSEMU2 remains the
reference backend; no alternate emulator was tested.
