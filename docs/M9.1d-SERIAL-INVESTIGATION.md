# M9.1d DOSEMU2 serial investigation

## Status: INCOMPLETE

The existing M9.1c COM1 failure remains preserved: both host-to-guest and
guest-to-host COM1 tests reported `Error reading from device COM1: Unknown error
code` with the DOSEMU2-created PTY and an external socat PTY pair. No CTTY result
is treated as UART proof.

The disposable qualification VM is reachable and was inspected without changing
production state:

* Debian GNU/Linux 13 (trixie), kernel `6.12.101+deb13-amd64`, x86_64;
* pinned DOSEMU2 2.0pre9 revision 7076 at the recorded `/opt` path;
* the preserved FreeDOS LiveCD mount is present;
* no physical serial device or public network was used.

An initial direct invocation exposed a packaging/runtime issue: the wrapper could
not load `libdosemu2.so`/FDPP libraries until the pinned `lib`, `lib/dosemu`, and
`lib/fdpp` directories were supplied through `LD_LIBRARY_PATH`. With those paths,
`dosemu --version` reports 2.0pre9 revision 7076, but this does not prove a guest
boot or serial operation. A minimal FreeDOS boot/BIOS INT 14h/UART reproducer and
PTY termios trace still need to be run in the VM.

Subsequent disposable-VM execution established real guest evidence. Running as
the unprivileged qualification user with the `kvm` group, `HOME`, `TERM`, and the
pinned library paths set, DOSEMU2 emitted the FreeDOS 1.4 banner and kernel 2043.
The first attempt lacked a materialized `COMMAND.COM` tree; copying the preserved
`FDOS-x86` working content into the disposable `drive_c` resolved that specific
guest-root issue. The resulting process reached the FreeDOS language prompt and
executed under the headless QEMU/libvirt VM. This is real boot evidence, but it
is not COM evidence.

The current remaining blocker is narrower: a direct BIOS INT 14h/UART utility and
raw PTY attachment have not yet been run. The observed DOSEMU2 diagnostics also
show KVM permission and console/audio warnings when the environment is incomplete;
those are invocation issues, not proof of a serial regression. Therefore no
conclusion is yet justified among FreeDOS/FDPP interaction, PTY behavior,
DOSEMU2 serial regression, or backend unsuitability.
The canonical backend remains `PARTIALLY_QUALIFIED`; M9.1a, M9.1b, M9.1c, and
M9.1d remain incomplete. No fallback emulator was substituted.

## Deterministic harness result (continuation)

A repository-owned harness now prepares a disposable working tree, writes a
non-interactive `FDCONFIG.SYS`/`AUTOEXEC.BAT`, creates a raw PTY, launches the
pinned DOSEMU2 configuration, and waits for bounded `SERIAL.READY`/result-file
evidence.  The DOS probe is a small NASM-built `.COM` image using BIOS INT 14h;
it expects `41 42 43` and replies `UBB-OK`.

The harness was executed in the Debian VM.  DOSEMU2 again booted the real
FreeDOS kernel and FreeCOM, but the guest reported `Bad command or filename`
for the probe on the mapped C: drive, so no serial bytes were sent and no COM
claim is made.  This is a concrete qualification-harness/filesystem execution
failure, not evidence of a UART regression; the next investigation must make
the DOS executable visible to the guest before serial diagnosis proceeds.

### 8.3/path follow-up

The original `SERIALTEST.COM` stem exceeded eight characters. The harness now
uses strict DOS names: `C:\UBBQUAL\UBBTEST.COM`, `READY.RST`, and
`SERIAL.RST`, with a fresh writable disposable drive tree. This removes the
long-name ambiguity and avoids modifying preserved media. DOSEMU2 reached
FreeCOM and the AUTOEXEC `MD` command in that tree.

On the subsequent Debian run, DOS still produced neither readiness nor result
file. The host used the bounded FreeDOS-kernel banner fallback and sent
`41 42 43`; no `UBB-OK` reply was received. Current evidence is therefore:

* DOS boot/AUTOEXEC: PASS;
* strict-name materialization: PASS on the host tree;
* host PTY/DOSEMU2 COM1 exchange: FAIL (no guest reply);
* guest result-file persistence: not observed.

This is now a genuine serial or DOSEMU2 host-drive write-path failure to be
diagnosed with BIOS/UART status and syscall tracing; it is not claimed as COM
qualification or backend rejection.
